# FY 用户反馈洞察

> 本地产品研究工具｜功能流程已实现｜模型语义质量待独立验证

## 问题：评论如何变成能讨论的产品问题？

我在座舱产品实践中接触过车机、语音助手、辅助驾驶与智能硬件反馈。手工整理时，一条评论可能有多种观点，粗略的正负标签无法解释用户具体评价了什么。后续独立项目围绕这个问题，建立从导入、拆分、核对到汇总的工具。

## 我的贡献

定义研究范围和模块/子功能，梳理有效反馈与内容噪音的边界，设计观点证据和人工复核流程；使用 AI 开发工具辅助完成本地实现，并根据首轮失败重新调整抽取、异常记录、并发与评测机制。

## 体验路径

导入样例 → 按编号去重 → 内容分流与多观点抽取 → 结构和原文证据校验 → 人工复核 → 模块看板与 CSV 导出。

## 一个例子

**合成原文：**“地图规划的路总是绕远，但是语音唤醒很快。”

| 观点 | 功能 | 情感 | 原文证据 |
|---|---|---|---|
| 路线规划绕远 | 车机 / 导航-路线规划 | 负面 | 地图规划的路总是绕远 |
| 语音唤醒快 | 语音助手 / 唤醒 | 正面 | 语音唤醒很快 |

这个例子用于解释结构，不是模型实测结果。工具中的截图样例由预设标注导入。

![原文与观点复核](assets/feedback-review.jpg)

## 三个产品取舍

1. **保留证据再汇总。** 标准标签可以概括功能，证据必须能在当前原文中核对，不能从上下文借来别人的观点。
2. **人工复核优先。** 模型结果可修改；人工改过的来源不被新的分析自动覆盖。不确定反馈保留待复核入口。
3. **成本和失败可见。** 开始前查看内容与预估费用；完成后区分成功、失败、跳过。用量未知时保留预算预留，而不是当成零费用。

## 迭代与验证

第一轮暴露出结构失败、串行耗时和默认看板范围的问题。我据此推动第二版增加错误分类、两路受限并发、多维内容分流和离线评估。公开版本的自动化检查验证的是导入、保存、原文校验和预算等机制；不能替代人工确认的语义效果。

现有工具提供独立评测入口，可比较有效反馈、模块、观点、证据及端到端遗漏。真实模型的准确性、速度和成本结论仍需相同样本与人工标准集测量。

## 面试可讲的能力

从用户研究定义标签体系；将模糊的“分析评论”拆成可验收任务；用真实失败改进流程；区分模型质量与程序正确性。
